Where Moodle puts a course action, and where it doesn't

Every screen an educator or a student can reach inside a course activity, classified by what sits in the bottom action zone. Four separate mechanisms currently compete for that zone, and 115 call sites explicitly switch one of them off. This is the inventory behind that number.

The four mechanisms

Every row in the inventory below is one of these. They are not variants of a single pattern — they are four independent implementations with different markup, different placement, and different rules about when they appear.

Pattern A

Bespoke core sticky footer

The page builds its own sticky_footer and fills it with whatever that screen needs — save buttons, paging, bulk tools, record navigation. No shared content contract.

core\output\sticky_footer · #sticky-footer
Pattern B

Linear navigation footer

Auto-injected on activity pages by a hook. Fixed contract: completion control, Previous, Next / Back to course. The only pattern nobody has to opt into.

supplementary_sticky_footer · .course-linear-navigation
Pattern C

Opted out, in-page actions

The page suppresses the footer and puts its save, submit or next control inline at the end of the form or content, where it scrolls away. The largest group by far.

set_show_navigation_footer(false) · .submitbtns · fitem_actionbuttons
Pattern D

Legacy activity navigation

The pre-4.0 in-page Previous / Jump to… / Next block. Self-suppresses wherever the course index is used, so it survives only in framed layouts and non-index formats.

output.activity_navigation · core_course/activity_navigation

What the divergence actually is

Only navigation was ever standardised. Saving was not.

Pattern B has a fixed, shared content contract and appears automatically. It is the one thing Moodle has genuinely converged on. But it carries navigation only — completion, Previous, Next. The moment a screen's primary action is Save, Submit or Post, there is no shared mechanism at all: the screen either builds its own footer from scratch (A) or drops the button inline and switches the footer off (C).

The dividing line is a single method on the form base class. Six forms in the whole codebase call it. Everything else gets an inline button.

lib/formslib.php → add_sticky_action_buttons() 6 callers, all in /grade/import + /grade/export lib/formslib.php → add_action_buttons() 78 callers in /mod alone

A student's core loop is almost entirely Pattern C.

Landing on an activity gives a student a sticky footer. Doing the activity takes it away. Attempting a quiz, editing an assignment submission, answering a feedback form, writing a wiki page, adding a database entry, assessing a workshop peer, posting to a forum — every one of these suppresses the footer and puts the primary action inline at the bottom of a long scroll.

So the sticky footer is present exactly where the stakes are lowest (reading a page) and absent exactly where they are highest (submitting work under a time limit).

Eight screens show two bottom-action zones stacked on top of each other.

Because Pattern B injects itself unless a page opts out, any activity landing page that already had its own in-page action ends up with both. A book chapter is the sharpest case: the in-page control is chapter Previous/Next, the sticky footer directly beneath it is activity Previous/Next. Two identical-looking pairs of arrows, ten pixels apart, doing entirely different things.

/mod/book/view.php #mod_book-chaptersnavigation → previous / next CHAPTER .stickyfooter → previous / next ACTIVITY

One navigation concept, split across two zones.

Three screens use the supplementary_content slot to put a "go back to the list" link in the sticky footer — but leave the prev/next controls for the same list rendered inline in the page body. Feedback response review is the clearest: "Go to all responses" is sticky, while "Previous response" and "Next response" are not.

/mod/feedback/show_entries.php sticky: Go to all responses in-page: ◀ Previous response Next response ▶

The assignment grader has its own private footer.

The grading app suppresses the navigation footer and builds a bespoke grade-actions-panel holding Save changes, Save and next, and Reset — pinned inside a resizable JS panel rather than in the page footer. The grading table one click away uses a real core sticky footer for its Save. Same activity, same task, two different mechanisms depending on which view the educator picked.

Two of five course formats can show the footer at all.

uses_linear_navigation() returns true only for Topics and Weeks. Social and Single activity inherit the base false, and because they also return false for uses_course_index(), they fall through to Pattern D — the legacy in-page block with the "Jump to…" dropdown. A course's format silently decides which of three navigation paradigms its activities get.

On top of that, Topics and Weeks courses expose enablelinearnav as a per-course setting, so an educator can turn the only standardised pattern off without realising what it governs.

The footer is a single-slot resource, and first writer wins.

The injection hook bails out if has_sticky_footer() is already true. Any page that renders its own footer therefore silently loses linear navigation — not as a design decision, but as a side effect of ordering. On the assignment grading table, an educator gets quick-grade Save and paging, and loses Previous/Next activity, with nothing in the UI explaining the trade.

course/format/classes/local/linearnavigationsettings.php:134 if ($page->has_sticky_footer()) { return false; } // no second footer, ever

The rules that decide, in order

Reproducing any row above means satisfying all five. Worth keeping to hand when testing on localhost — most "the footer isn't showing" cases are rule 2 or rule 5.

1
Must be an activity page. $PAGE->cm !== null. Course-level screens never get Pattern B, only Pattern A if they build one.
2
Nothing else claimed the footer. has_sticky_footer() must still be false when the footer hook runs.
3
The page didn't opt out. should_show_navigation_footer() — false on all 115 call sites listed as Pattern C.
4
The format supports it and the course enabled it. uses_linear_navigation() (Topics, Weeks only) and the enablelinearnav course format option.
5
Not a stealth activity unless the viewer holds moodle/course:viewhiddenactivities.
